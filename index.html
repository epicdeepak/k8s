1. The Kubernetes mental model

Before typing commands, answer four questions: Where? Which area? What? Why?

WHERE? Context Which cluster and credentials?
WHICH AREA? Namespace Which logical workspace?
WHAT? Resource Deployment, Pod, Service...
WHY? Observe Status → logs → describe → events
Context cluster + user + namespace
→
Namespace logical boundary
→
Deployment desired application state
→
ReplicaSet maintains Pod count
→
Pod runs containers
Core idea: Kubernetes is a system where you declare the desired state and controllers continuously work toward making the actual cluster match that desired state.

2. Context & Namespace

Think: Context = Where am I?
Namespace = Which area am I looking at?

Context

A context generally tells kubectl which cluster and credentials to use and which namespace should be the default.

kubectl config current-context kubectl config get-contexts kubectl config use-context <context>

Namespace

A namespace is a logical partition inside a Kubernetes cluster.

kubectl get ns kubectl get pods -n payments
kubectl
kubectl config current-context kubectl config use-context staging kubectl get pods -n payments
K9s
k9s :ctx :ns :po
Safety habit: Before editing or deleting anything, verify your context and namespace.

3. What actually runs?

Kubernetes has many resource types. Start with these.

Deployment

Defines how an application should run, including its Pod template and replica count.

ReplicaSet

Ensures the desired number of matching Pods exists.

Pod

Smallest deployable unit. Contains one or more containers.

Service

Gives a stable network endpoint for a group of Pods.

Ingress

Routes external HTTP/HTTPS traffic toward Services.

Job / CronJob

Runs work to completion, either once or on a schedule.

Ingress external HTTP
→
Service stable endpoint
→
Pods application containers

4. Pods: the thing you debug most

Pod status is a clue, not the complete diagnosis.

Running Pod is running. Containers may still fail readiness.
Pending Pod has not fully started. Check scheduling/resources.
ContainerCreating Container setup is in progress.
CrashLoopBackOff Container repeatedly exits.
ImagePullBackOff Kubernetes cannot pull the image.

Read a Pod like an operator

Signal Ask Next action
READY Are the expected containers ready? describe + logs
STATUS What lifecycle state is it in? Use status to choose investigation
RESTARTS Is the container repeatedly dying? logs --previous + describe
AGE Did this Pod appear recently? Compare with deployment timing

5. Production debugging flow

Example: "The API is failing." Don't jump randomly between resources.

01 Context Right cluster?
02 Namespace Right area?
03 Deployment → Pods Is workload healthy?
04 Status READY / STATUS / RESTARTS
05 Logs What is the app saying?
06 Describe What does Kubernetes know?
07 Events What happened recently?
08 Service Can traffic reach Pods?
kubectl path
kubectl config current-context kubectl get pods -n <namespace> kubectl logs <pod> -n <namespace> kubectl logs <pod> --previous -n <namespace> kubectl describe pod <pod> -n <namespace> kubectl get events -n <namespace> kubectl get svc -n <namespace>
K9s path
:ctx :ns :deploy :po l # logs f # follow logs d # describe :events :svc s # shell

6. Same task, two interfaces

kubectl is the command-line client. K9s is an interactive terminal UI for Kubernetes.

Use case kubectl K9s
See current context kubectl config current-context :ctx
List namespaces kubectl get ns :ns
List Pods kubectl get pods :po
Deployments kubectl get deploy :deploy
Services kubectl get svc :svc
Inspect resource kubectl describe pod <pod> Select → d
View logs kubectl logs <pod> Select → l
Follow logs kubectl logs -f <pod> Select → f
Shell into Pod kubectl exec -it <pod> -- /bin/sh Select → s
Events kubectl get events :events
Delete resource kubectl delete … Select → Ctrl+d

K9s keybindings can vary by version/configuration. Press ? inside K9s to see the active bindings.

7. Common use cases

kubectl

kubectl get pods kubectl logs <pod> kubectl logs <pod> --previous kubectl describe pod <pod> kubectl get events

K9s

:po select Pod → l select Pod → d :events
Investigation first. Observe before changing resources.

kubectl

kubectl get pods kubectl logs <pod> --previous kubectl describe pod <pod>

K9s

:po check RESTARTS l d

Common investigation areas: application exits, probes, configuration, dependencies, memory/resource limits, node events.

kubectl

kubectl get svc kubectl describe svc <service> kubectl get pods --show-labels

K9s

:svc select Service → d :po inspect labels

Services route traffic to Pods using selectors. If the selector does not match the intended Pods, traffic will not reach them.

kubectl

kubectl get deploy kubectl rollout status deployment/<name> kubectl describe deployment <name>

K9s

:deploy inspect: READY UP-TO-DATE AVAILABLE d

Follow the chain: Deployment → ReplicaSet → Pods.

8. Production safety

Make “where am I?” a reflex before every change.

Read-only investigation

kubectl config current-context kubectl get pods kubectl describe pod <pod> kubectl logs <pod> kubectl get events

Potentially destructive

kubectl edit … kubectl delete … kubectl scale … kubectl rollout …
Before modifying or deleting anything: verify the context, verify the namespace, identify the exact resource, and understand the expected effect.

9. The small set worth memorizing

You do not need to memorize Kubernetes. Memorize the investigation path.

WHERE

kubectl config current-context :ctx

AREA

kubectl get ns :ns

WORKLOAD

kubectl get pods :po

WHY

kubectl logs <pod> kubectl describe pod <pod>

EVENTS

kubectl get events :events

NETWORK

kubectl get svc :svc
One-line memory: Context → Namespace → Deployment → Pod → Status → Logs → Describe → Events → Service
Important distinction: Kubernetes is the platform/system. kubectl is the CLI you use to interact with it. K9s is an interactive terminal UI that helps you navigate and operate those same Kubernetes resources.
