01 · Start here

Kubernetes is a control system

The most useful architectural mental model is: you describe desired state → Kubernetes observes actual state → controllers continuously reconcile the difference.

02 · Control loop

What happens when you run kubectl apply?

A YAML file is not the thing that actually runs your application. It is an instruction submitted to the Kubernetes API.

1 · kubectl Sends API request
2 · API Server Auth / admission / validation
3 · Desired State Stored as cluster state
4 · Controllers Reconcile actual state
5 · Nodes Kubelet runs workloads

Desired state

Example: "I want 3 replicas of version 1.4 of my API."

kubectl apply -f deployment.yaml

Actual state

Maybe only 2 Pods are healthy because the third Pod cannot schedule or pass readiness.

kubectl get deployment kubectl get pods kubectl get events
Kubernetes is not simply: "run this container." It is much closer to: "maintain this system state."
03 · Where am I?

Context, cluster and namespace

Most dangerous Kubernetes mistakes start with operating in the wrong context.

Context

A kubeconfig context selects the Kubernetes cluster, user/credentials and default namespace.

Cluster

The Kubernetes environment containing the control plane and worker nodes.

Namespace

A logical boundary for namespaced resources such as Pods, Deployments, Services and Secrets.

kubectl config get-contexts kubectl config current-context kubectl config view --minify kubectl config use-context <context>
kubectl get namespaces kubectl get pods -n <namespace> kubectl get svc -n <namespace>
Production reflex: Before: delete edit scale rollout first verify: context → namespace → resource → expected effect
K9s equivalent
k9s :ctx :ns

K9s can also be launched against a specific context or namespace.

k9s --context <context> k9s -n <namespace> k9s --readonly
04 · Workload architecture

Deployment vs StatefulSet vs DaemonSet vs Job

The workload type should follow the application's behavior, not the other way around.

Deployment

Best mental model: interchangeable/stateless application replicas.

API servers · web apps · workers

StatefulSet

Use when individual replicas need stable identity, stable storage or ordered operations.

MongoDB · Kafka · ZooKeeper-style workloads

DaemonSet

Ensures a workload runs on nodes matching its placement rules.

log agents · node monitoring · CNI components

Job / CronJob

Work that finishes rather than continuously serving traffic.

migrations · backups · scheduled reports
Deployment ReplicaSet
→
ReplicaSet Pod replicas
→
Pod Container(s)
StatefulSet insight: StatefulSets provide stable identity and are designed for applications that need persistent storage and/or stable network identity. Individual Pods are not interchangeable in the same way that Deployment replicas generally are. :contentReference[oaicite:1]{index=1}
05 · Pod anatomy

A Pod is a runtime boundary

Containers inside a Pod share the Pod's network namespace and can share mounted volumes. The Pod is the unit Kubernetes schedules.

Pod
Container Application
Sidecar Supporting process
Network Pod IP / ports
Volumes Mounted storage
ServiceAccount Identity

Pod status → what should I investigate?

Running Running does not automatically mean ready or healthy.
Pending Scheduling, resources, affinity, taints or volumes.
CrashLoopBackOff Repeated container exits. Inspect previous logs and termination state.
ImagePullBackOff Image, registry, credentials or network problem.
ContainerCreating Image, volume, networking or runtime setup.
kubectl get pods -o wide kubectl describe pod <pod> kubectl logs <pod> kubectl logs <pod> --previous
:po select Pod l # logs d # describe s # shell
Architect question: "Running" vs "Ready"
A container can be running while its readiness probe says: "Do not send traffic here." This is why a healthy investigation should separate:

Process alive? → Container ready? → Pod selected by Service? → Network reachable?
06 · Networking

Trace the request instead of guessing

A Service is a stable abstraction over a changing set of Pods. Kubernetes uses selectors and EndpointSlices to connect the two.

External traffic
Client Browser / API consumer
Load Balancer Cloud / infrastructure
Ingress / Gateway HTTP routing
Kubernetes service layer
Service Stable endpoint
EndpointSlice Backend endpoints
Pod IP Actual workload endpoint

Debug a Service

kubectl get svc -n <ns> kubectl describe svc <svc> -n <ns> kubectl get endpointslice -n <ns> kubectl get pods --show-labels -n <ns>

K9s path

:svc select Service d :po inspect labels
A Service normally selects Pods through labels and Kubernetes maintains EndpointSlices representing the service backends. This is why debugging should follow: Service → selector → EndpointSlice → Pod rather than only looking at the Service object. :contentReference[oaicite:2]{index=2}
In-cluster DNS mental model
A typical Kubernetes Service can be referenced through DNS using its Service name and namespace.

Example:
mongo.data.svc.cluster.local
Inside the same namespace, the shorter name may often be sufficient:
mongo
For a StatefulSet with a governing Headless Service, individual Pods can also have stable DNS identities. :contentReference[oaicite:3]{index=3}
NetworkPolicy mental model
NetworkPolicy can restrict traffic at the Pod/network level, but enforcement depends on the cluster's networking plugin supporting NetworkPolicy.

Architect question: "Can DNS resolve?" is different from: "Is traffic allowed?" which is different from: "Is the destination accepting traffic?" :contentReference[oaicite:4]{index=4}
07 · Storage

Container storage is not automatically durable storage

For stateful systems, distinguish the Pod lifecycle from the storage lifecycle.

Application
Pod Container filesystem
Kubernetes storage abstraction
PersistentVolumeClaim Application request
PersistentVolume Actual cluster storage
StorageClass Provisioning profile
Infrastructure
Cloud Disk EBS / PD / Disk etc.
Network Storage NFS / CSI backend
kubectl get pvc -A kubectl get pv kubectl get storageclass kubectl describe pvc <claim> -n <namespace>
For a database incident, never reason only from: Pod = Running Also ask: Is the PVC bound? Where is the volume? What happens to it if the Pod moves? What are the backup/restore guarantees?
08 · Real production use case

MongoDB is running on Kubernetes — how do I access it?

Start by discovering the deployment model. Do not immediately exec into a random Pod.

Step 1 — Discover how MongoDB is deployed
Deployment? StatefulSet? Operator? Replica set? Service?
kubectl get pods -n <mongo-namespace> -o wide kubectl get deploy,sts,svc,pvc -n <mongo-namespace> kubectl get pods -n <mongo-namespace> --show-labels
If MongoDB is deployed as a StatefulSet, expect stable Pod identities and persistent storage. If an operator manages it, inspect the operator's Custom Resource as well as the generated Kubernetes resources.
Step 2 — Find the network entry point
Service → endpoint → MongoDB Pods
kubectl get svc -n <mongo-namespace> kubectl describe svc <mongo-service> \ -n <mongo-namespace> kubectl get endpointslice \ -n <mongo-namespace>
:svc select MongoDB Service d :po inspect MongoDB Pods
Step 3 — Connect from your laptop using port-forward
Excellent for controlled debugging/admin access
kubectl port-forward \ -n <mongo-namespace> \ svc/<mongo-service> \ 27017:27017

Then in another terminal:

mongosh \ "mongodb://127.0.0.1:27017/<database>" \ --username <user> \ --authenticationDatabase admin
MongoDB's documentation shows mongosh connecting to localhost on port 27017, while Kubernetes documents kubectl port-forward specifically as a useful mechanism for database debugging. :contentReference[oaicite:5]{index=5}
Important: Port-forward is an access/debugging technique. It is not the same thing as designing a production network path for your application. Kubernetes also notes that port-forward access is governed by RBAC and can provide direct network access to workloads. :contentReference[oaicite:6]{index=6}
Step 4 — Connect from inside the cluster
Often the better method for testing application-to-database connectivity

If you already have a Pod containing mongosh, connect to the MongoDB Service DNS name:

kubectl exec -it <client-pod> \ -n <application-namespace> \ -- mongosh \ "mongodb://<mongo-service>.<mongo-namespace>.svc.cluster.local:27017/<database>" \ --username <user> \ --authenticationDatabase admin

If that Pod does not contain mongosh, use an approved database client/debug image rather than modifying the production application container.

kubectl run mongo-client \ -n <mongo-namespace> \ --rm -it \ --restart=Never \ --image=<approved-mongo-client-image> \ -- mongosh \ "mongodb://<mongo-service>:27017/<database>"
Step 5 — Now actually run MongoDB queries
Start with safe observational queries

Understand the database

show dbs use appdb show collections db.stats()

Inspect data

db.users.find({ status: "active" }).limit(20) db.orders.countDocuments({ status: "pending" })

Inspect indexes

db.users.getIndexes() db.orders.getIndexes()

Investigate a query

db.users .find({email:"user@example.com"}) .explain("executionStats")
Run expensive queries carefully in production. "Read-only" does not mean "zero operational impact." An execution-plan investigation, aggregation, collection scan or large result set can still consume CPU, memory or I/O.
Step 6 — Authentication and Secrets
Separate Kubernetes identity from MongoDB identity

Kubernetes side

kubectl get secret -n <mongo-namespace> kubectl describe secret \ <mongo-secret> \ -n <mongo-namespace>

MongoDB side

mongosh \ "mongodb://<host>:27017/<db>" \ --username <user> \ --authenticationDatabase admin
Do not casually paste credentials into shell history, screenshots, tickets or chat. Kubernetes Secrets are specifically intended for sensitive data, but the default storage model in Kubernetes does not make them automatically equivalent to a fully protected external secret system. :contentReference[oaicite:7]{index=7}
Step 7 — TLS / Replica Set
Where architect-level database access differs from a toy Pod

For a TLS-enabled MongoDB deployment:

mongosh \ "mongodb://mongo-0.example:27017,\ mongo-1.example:27017,\ mongo-2.example:27017/?replicaSet=rs0" \ --tls \ --tlsCAFile /path/to/ca.pem
MongoDB documents replica-set connection strings using multiple members and TLS configuration with a CA file. :contentReference[oaicite:8]{index=8}
Key architectural distinction: port-forwarding a single Pod is not automatically equivalent to connecting to the MongoDB replica set as a whole. For production connectivity, understand: topology → replica-set discovery → TLS → authentication → read preference → failover
MongoDB workflow in K9s
Visual investigation without losing the architecture
:ctx :ns :sts :po :svc :pvc

From the Pod view:

l # Logs d # Describe s # Shell Shift-F # Port-forward

K9s also exposes a port-forward view and can create a port-forward from the Pod view. :contentReference[oaicite:9]{index=9}

For architect-level troubleshooting, use K9s for navigation/observation and kubectl for precise, reproducible commands you can put into runbooks and automation.
09 · Security

Identity has multiple layers

Kubernetes identity and application/database identity are different.

Human → Kubernetes

kubeconfig / identity provider / Kubernetes RBAC.

Pod → Kubernetes API

ServiceAccount + RBAC determine what the workload can request from the API.

Application → MongoDB

MongoDB username, authentication database, authorization and TLS.

Network

NetworkPolicy and the cluster networking implementation control allowed traffic paths.

Secrets

Kubernetes Secret or external secret-management integration.

Admission

Policy can validate or mutate workloads before they are accepted.

Think in a chain: Who am I? → What Kubernetes API can I access? → What Pod can I access? → What network path exists? → What database identity do I have?
10 · Production debugging

Follow the dependency graph

Don't run 30 commands. Ask one question at every layer.

1 · Location

kubectl config current-context kubectl get ns

2 · Workload

kubectl get deploy kubectl get pods

3 · Application

kubectl logs <pod> kubectl logs <pod> --previous

4 · Kubernetes

kubectl describe pod <pod> kubectl get events

5 · Network

kubectl get svc kubectl get endpointslice

6 · Dependency

kubectl exec -it <pod> -- \ curl http://<service>:<port>
Start with: STATUS → RESTARTS → current logs → previous logs → describe → events
kubectl get pod <pod> -o wide kubectl logs <pod> kubectl logs <pod> --previous kubectl describe pod <pod> kubectl get events --sort-by=.lastTimestamp

Service path

kubectl get svc <service> kubectl describe svc <service> kubectl get endpointslice \ -l kubernetes.io/service-name=<service>

Pod path

kubectl get pods --show-labels kubectl exec -it <client-pod> -- \ getent hosts <service>
Separate DNS failure from network-policy failure from application-port failure.
kubectl get sts,svc,pods,pvc -n <mongo-ns> kubectl get pods -n <mongo-ns> -o wide kubectl get pvc -n <mongo-ns> kubectl get endpointslice -n <mongo-ns> kubectl logs <mongo-pod> -n <mongo-ns> kubectl describe pod <mongo-pod> -n <mongo-ns>
Then separate: Kubernetes problem from: MongoDB process problem from: Storage problem from: Authentication/TLS problem from: Replica-set/topology problem
11 · Architect checklist

What should you think about beyond kubectl?

Architect-level Kubernetes work is about system properties, not just commands.

Availability

Replicas, zones, topology spread, PodDisruptionBudget, failover.

Capacity

Requests, limits, autoscaling, node pools and headroom.

Scheduling

Taints, tolerations, affinity, anti-affinity and topology.

Networking

Service discovery, DNS, ingress/gateway, policies and egress.

Storage

StorageClass, PVC/PV, performance, backup and restore.

Security

RBAC, ServiceAccounts, Secrets, admission and network policies.

Observability

Logs, metrics, traces, events and alerting.

Delivery

GitOps, rollout strategy, canary, rollback and policy checks.

Failure domains

Node, zone, region, storage failure and application failure.

Scheduling example: why did Kubernetes place this Pod there?
Investigate:

nodeSelector nodeAffinity podAffinity podAntiAffinity taints/tolerations topologySpreadConstraints

Kubernetes provides several mechanisms for influencing Pod placement, including node selectors, affinity/anti-affinity and topology spread constraints. :contentReference[oaicite:10]{index=10}
Stateful application checklist
For MongoDB, Kafka, Elasticsearch-like workloads, ask:

Identity
Does every replica need a stable name?

Storage
Does each replica need durable storage?

Topology
Can replicas survive a node or zone failure?

Backup
How do we restore data?

Recovery
What happens when a Pod disappears?

Application protocol
Does the database have its own cluster/leader/replica-set semantics that Kubernetes does not understand automatically?
Key architectural principle: Kubernetes can manage the lifecycle of a stateful workload, but Kubernetes itself is not the database's replication protocol, consistency model, backup system or application-level failover logic.

Final mental model

When something is broken, walk the layers

1 · LOCATION
Context Correct cluster?
Namespace Correct boundary?
2 · WORKLOAD
Deployment Desired replicas
StatefulSet Stateful identity
Pod Actual runtime
3 · RUNTIME
Status Running?
Ready Accepting traffic?
Logs Application signal
Events Kubernetes signal
4 · NETWORK
Service Stable endpoint
EndpointSlice Actual backends
DNS Name resolution
NetworkPolicy Allowed traffic?
5 · DATA
PVC Requested storage
PV Bound storage
Database Application state
6 · SECURITY
RBAC Who can do what?
ServiceAccount Workload identity
Secret Credentials
TLS Transport security
The architect's debugging loop:

WHERE am I? → WHAT workload is responsible? → IS the Pod actually healthy? → CAN traffic reach it? → CAN it reach its dependencies? → IS storage healthy? → IS authentication/TLS correct? → WHAT does the application/database itself report?
